# PlayCards — текущая спецификация игры

Этот документ описывает текущее поведение проекта PlayCards: онлайн-игра в «Дурака» на Blazor Server + SignalR с комнатами, ботами и rematch-механикой.

Документ нужно обновлять при каждом изменении правил, жизненного цикла комнаты, поведения ИИ, UI-кнопок или сетевой логики.

---

## 1. Назначение проекта

PlayCards — браузерная онлайн-игра в «Дурака».

Основные возможности:

- создание комнаты;
- вход в комнату по коду;
- reconnect после обновления страницы;
- игра человека против людей и/или ИИ;
- добавление ИИ до старта партии;
- ход атаки и защиты через SignalR;
- таблица результатов;
- rematch после окончания партии;
- визуальный эффект победы/поражения после окончания партии;
- ИИ-боты с Gemini-подсказчиком и серверной валидацией правил.

---

## 2. Технологии

Текущий стек:

- ASP.NET Core;
- Blazor Server;
- SignalR;
- C#;
- in-memory состояние комнат;
- CSS-анимации для end-game эффектов;
- Gemini API для советов ИИ, если задан API key через environment variable.

Состояние игры хранится в памяти сервера. После рестарта сервера комнаты, руки, память ИИ и история исчезают.

---

## 3. Комнаты

Комната содержит:

- код комнаты;
- имя комнаты;
- список игроков;
- фазу игры;
- колоду;
- козырь;
- стол;
- текущего атакующего;
- текущего защитника;
- список игроков, которые пасанули;
- список игроков, готовых продолжить;
- таблицу побед/поражений;
- служебный лог;
- видимую историю карт для ИИ;
- приватную память каждого ИИ.

Фазы комнаты:

- `Lobby` — комната создана, игра ещё не началась;
- `Playing` — партия идёт;
- `Finished` — партия закончена, доступно продолжение или выход.

---

## 4. Лимит игроков

Общий лимит комнаты:

```text
люди + ИИ <= 6
```

Это сделано, чтобы на всех хватало карт в стандартной колоде.

Дополнительное правило:

```text
ИИ максимум 3
```

Примеры:

- 5 людей + 1 ИИ — можно;
- 4 людей + 2 ИИ — можно;
- 3 людей + 3 ИИ — можно;
- 6 людей + 0 ИИ — можно;
- 6 людей + 1 ИИ — нельзя;
- 4 людей + 3 ИИ — нельзя, потому что всего 7 игроков.

---

## 5. Добавление ИИ

ИИ можно добавлять только до старта партии, пока комната находится в `Lobby`.

Кнопка добавления ИИ должна отображаться только:

- внутри комнаты;
- в фазе `Lobby`;
- если общее количество игроков меньше 6.

Кнопка не должна отображаться вне комнаты.

Сервер всё равно обязан проверять лимиты независимо от UI.

---

## 6. Reconnect и обновление страницы

Игрок может обновить страницу и вернуться в комнату через данные из `localStorage`:

- `playcards.roomCode`;
- `playcards.playerId`;
- `playcards.playerName`.

Если reconnect успешен, игрок возвращается в свою комнату.

Если reconnect неуспешен, клиент должен очистить stale localStorage и дать игроку нормально создать новую комнату или войти в другую.

В комнате с ИИ человек не считается ушедшим только из-за refresh/disconnect. Если человек явно не нажимал «Выйти», он должен иметь возможность вернуться обратно.

---

## 7. Отключение игрока

Если человек просто потерял соединение или обновил страницу:

- он становится disconnected;
- его нельзя считать явно вышедшим;
- если в комнате есть ИИ, комната должна ждать его возвращения;
- ИИ не должны уничтожаться только из-за временного disconnect человека.

Если человек явно нажимает «Выйти»:

- он удаляется из комнаты;
- если после этого остались только ИИ, комната уничтожается;
- память ИИ и история очищаются.

---

## 8. Старая сессия

Старая/мусорная сессия — это не любой disconnect.

Старая сессия считается мусорной, если:

```text
комната Finished
и живых людей в ней нет
```

Также мусорной считается ситуация, когда человек явно вышел, а в комнате остались только ИИ.

При уничтожении комнаты очищаются:

- руки игроков;
- руки ИИ;
- `BotMemory`;
- `CardMemoryLog`;
- `SeenCardCodes`;
- стол;
- passed/continue sets;
- сама комната удаляется из памяти сервера.

---

## 9. Правила партии

Игра использует правила «Дурака» в текущей серверной реализации.

Основные правила:

- атакующий кладёт карту на стол;
- защитник должен побить карту;
- защитник может взять карты;
- подкидывать можно только карту ранга, который уже есть на столе;
- нельзя подкинуть больше карт, чем защитник физически может отбить;
- игрок без карт при пустой колоде больше не должен быть активным атакующим или защитником;
- если игрок закончил карты при пустой колоде, он ждёт окончания партии другими игроками;
- партия заканчивается, когда остаётся один игрок с картами или активных игроков больше нет.

---

## 10. Атака и подкидывание

Начальная атака:

- ходит текущий атакующий;
- если стол пустой, атаковать может только текущий атакующий.

Подкидывание:

- подкидывать можно только карту того ранга, который уже есть на столе среди атакующих или защитных карт;
- подкидывать может любой не-защитник, если он ещё не пасанул;
- если человек может подкинуть, боты не должны мгновенно закрывать раунд;
- если один атакующий пасанул, но после новой защиты на столе появился новый ранг, другой игрок или бот может снова получить возможность подкинуть.

Ожидаемый сценарий:

```text
ИИ1 атакует 6
ИИ2 отбивается 7
человек подкидывает 7
ИИ2 отбивается 8
если человеку нечего подкинуть, но у ИИ1 есть карта подходящего ранга — ИИ1 может снова подкинуть
так продолжается, пока защитник не возьмёт или пока атакующие не пасанут/не смогут подкинуть
```

---

## 11. Защита

Защитник:

- должен побить каждую неотбитую атакующую карту;
- может взять карты;
- не должен быть обычным атакующим в этом же раунде;
- при защите карта должна бить атакующую по масти/рангу или козырем.

В UI защита может работать двумя способами:

1. выбрать неотбитую карту на столе, потом карту из руки;
2. fallback: если игрок-защитник нажал карту из руки, сервер может попробовать применить её к первой неотбитой карте.

---

## 12. Пас / Бито

Игроки, которые не защищаются, могут пасовать.

Раунд закрывается как «Бито», когда:

- все карты на столе отбиты;
- все актуальные атакующие/подкидывающие пасанули или не имеют легальных подкидываний;
- больше нет действий, которые должны ждать человека.

После «Бито»:

- карты со стола уходят из игры;
- руки пополняются из колоды;
- следующий ход получает бывший защитник, если он ещё играет.

---

## 13. Взять

Если защитник берёт:

- все карты со стола переходят в руку защитника;
- стол очищается;
- руки пополняются из колоды;
- следующий атакующий выбирается среди активных игроков;
- игроки без карт при пустой колоде пропускаются.

---

## 14. Окончание партии

Партия заканчивается, когда:

- колода пустая;
- один или несколько игроков уже без карт;
- остаётся только один игрок с картами, который считается проигравшим;
- или активных игроков больше нет.

Игроки с 0 карт при пустой колоде считаются закончившими и ждут, пока остальные доиграют.

Они не должны становиться атакующими или защитниками.

---

## 15. Визуальные эффекты окончания партии

После перехода партии в `Finished` клиент показывает короткий визуальный эффект для текущего игрока.

Правило определения результата на клиенте:

- если у текущего игрока `0` карт — он считается победителем и видит салют;
- если у текущего игрока остались карты — он считается проигравшим и видит много слов «ха».

Эффекты:

- победитель: салют/confetti около 3 секунд;
- проигравший: слова «ха» появляются в случайных позициях и исчезают примерно за 700ms;
- общий поток появления длится около 3 секунд;
- эффект срабатывает один раз на конкретное окончание партии;
- при новой партии эффект не должен повторяться от старого `Finished`-состояния.

Эти эффекты являются UI-only. Они не должны менять серверное состояние, результат партии, победы/поражения или логику rematch.

---

## 16. Rematch / Продолжить

После окончания партии появляется блок:

- «Продолжить»;
- «Выйти».

Для игры с ИИ правило особое:

- если живой человек нажимает «Продолжить», все ИИ автоматически считаются готовыми;
- новая партия с ИИ должна стартовать сразу;
- не надо ждать 15-секундный rematch timer;
- память ИИ очищается перед новой партией;
- сами ИИ остаются в комнате.

Перед новой партией очищаются:

- `BotMemory` каждого ИИ;
- `CardMemoryLog`;
- `SeenCardCodes`;
- `PassedPlayerIds`.

Смысл: боты не должны отправлять Gemini историю прошлой партии.

---

## 17. Выход из комнаты

Если человек нажимает «Выйти»:

- человек покидает комнату;
- если это игра с ИИ, ИИ удаляются;
- память ИИ очищается;
- если людей больше нет, комната удаляется.

Это отличается от refresh/disconnect. Refresh не должен считаться выходом.

---

## 18. ИИ-боты

ИИ-боты состоят из двух уровней:

1. серверная валидация правил;
2. Gemini-подсказчик для выбора карты из разрешённых вариантов.

Сервер всегда должен оставаться главным источником истины.

Gemini может советовать, но сервер обязан проверять:

- есть ли карта в руке бота;
- является ли карта легальной;
- можно ли сейчас атаковать;
- можно ли подкинуть;
- не превышен ли лимит карт против защитника;
- не закончились ли карты у бота.

Если Gemini недоступен или совет некорректен, бот использует fallback-логику.

---

## 19. Что ИИ может знать

ИИ конкретного бота может получать:

- свои карты;
- текущий стол;
- козырь;
- количество карт у игроков;
- видимую историю карт;
- личную память этого бота;
- общие round limits: сколько карт у защитника, сколько атак на столе, сколько ещё можно подкинуть.

ИИ не должен получать напрямую:

- карты на руках человека;
- карты на руках других ИИ;
- закрытую колоду.

Если карта была публично раскрыта на столе, ИИ может помнить это как видимое событие. Если затем карта попала в руку игрока после «Взять», это считается знанием из открытого прошлого события, а не прямым раскрытием чужой руки.

---

## 20. Память ИИ

У каждого ИИ есть своя `BotMemory`.

Также есть общий видимый журнал `CardMemoryLog`.

Правило памяти:

- в пределах одной партии ИИ может использовать историю видимых событий;
- после `Continue` память ИИ должна очищаться;
- новая партия начинается с чистой ИИ-памятью;
- при выходе человека и удалении ИИ память уничтожается полностью.

## 22. Текущие важные сервисы и компоненты

Основные серверные сервисы:

- `GameRoomService` — основное состояние игры и базовые действия;
- `BotPlayerService` — логика действий ИИ;
- `AiMoveAdvisorService` — Gemini-подсказчик;
- `TurnRulesService` — дополнительные правила хода и защита от нелегальных переходов;
- `SmartDefenseService` — fallback-защита при клике картой из руки;
- `ConnectionRecoveryService` — восстановление игрока после refresh/reconnect;
- `BotSessionLifecycleService` — lifecycle ИИ при continue/leave/stale sessions;
- `BotRoomReconnectProtectionService` — защита disconnected-человека в комнате с ИИ;
- `DisconnectedPlayerCleanupService` — фоновые таймеры, cleanup и запуск бот-ходов.

Важные UI-компоненты:

- `EndGameEffect.razor` — UI-only эффект победы/поражения;
- `BotControls.razor` — добавление ИИ в Lobby.

## 23. Инварианты, которые нельзя ломать

При любых изменениях нельзя нарушать эти правила:

1. Люди + ИИ в комнате максимум 6.
2. ИИ максимум 3.
3. ИИ нельзя добавлять после старта партии.
4. Кнопка ИИ не должна отображаться вне комнаты.
5. Игрок без карт при пустой колоде не должен быть атакующим/защитником.
6. Человек после refresh/disconnect должен иметь возможность вернуться, если явно не нажимал «Выйти».
7. Если человек явно вышел, ИИ и их память удаляются.
8. После `Continue` память ИИ прошлой партии очищается.
9. Gemini не должен получать прямые чужие руки и закрытую колоду.
10. Серверная валидация важнее ответа ИИ.
11. Нельзя полагаться только на UI для правил игры.
12. Любой новый action в Hub должен после изменения состояния делать broadcast актуального состояния комнаты.
13. UI-only эффекты окончания партии не должны менять серверное состояние.

## 26. Известные технические долги

Текущая архитектура уже работает, но есть технические долги:

- часть новых сервисов использует reflection для доступа к приватным полям `GameRoomService`;
- в будущем лучше выделить официальный `RoomRepository` или сделать методы `GameRoomService` публичными для lifecycle/rules;
- `GameRoomService` стоит постепенно разгрузить от правил и lifecycle;
- UI `Index.razor` крупный, его желательно разбить на компоненты;
- Gemini-вызов синхронный и может тормозить ход, лучше вынести AI-call вне lock с revalidate/commit;
- скрытую колоду не стоит отправлять клиенту полностью, если нужна защита от client-side cheating.

---

## 27. Текущий принцип разработки

При изменениях лучше делать маленькие коммиты:

- один коммит — один смысл;
- после commit нужно fetch-проверкой убедиться, что файл реально обновился;
- не заявлять «готово», пока GitHub не подтвердил и содержимое не проверено;
- большие full-file updates лучше избегать;
- сначала фиксировать серверные правила, потом UI;
- UI не должен быть единственным ограничителем правил.
